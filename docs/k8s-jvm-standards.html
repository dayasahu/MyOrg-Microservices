Platform Standards

Kubernetes & JVM Standards

Organization-wide best practices for sizing, tuning, and operating Spring Boot microservices on Kubernetes — with rationale, trade-off analysis, and decision rules for every common service pattern.

How to use this guide. Each section explains the why, not just the what. Every recommendation includes a trade-off table, override conditions, and callouts for specific service patterns — Kafka consumers, schedulers, async pipelines, state machines, and bulky services each behave differently under load, and are called out explicitly.

1 Kubernetes Resource Sizing

Requests vs Limits — The Fundamental Distinction

Kubernetes uses requests to schedule (find a node that has enough headroom) and limits to enforce (cap what a container may consume).

SettingScheduler uses it?Runtime enforcementExceed behaviour
CPU RequestYes — finds node with spare CPULinux CFS shares (weighted)Under node contention, pod gets proportionally less CPU time. On an idle node it can freely burst above its request up to any limit (or node capacity if no limit).
CPU LimitNoCFS bandwidth control (hard quota)Throttled even if node is idle
Memory RequestYes — finds node with spare RAMSoft reservationPod may be evicted under node pressure
Memory LimitNocgroup memory limit (hard)OOMKilled — container restarted
The most misunderstood rule. CPU throttling occurs at the limit, not at saturation. A pod with limit: 500m running on a node at 10% CPU will still be throttled if it tries to use 501m for even 1ms — this is CFS bandwidth throttling and it is the root cause of latency spikes that appear despite low node CPU utilisation. It is distinct from the noisy neighbour problem (where one pod starves others on the same node). Here only the throttled pod suffers, and the node CPU graph shows nothing unusual.

QoS Classes — Why They Matter

ClassConditionEviction priorityRecommendation
Guaranteedrequest = limit for all resourcesLast to be evictedProduction APIs, stateful services
Burstablerequest < limitMiddleBatch jobs, background workers
BestEffortNo requests or limits setFirst to be evictedNever in production

Memory always: request = limit. Unlike CPU, JVM heap is a fixed allocation — there is no "burst" benefit. Setting memory request below limit creates Burstable QoS and risks eviction under node pressure, even when the pod is behaving normally.

Persistent long-lived connections
CPU request500m

Memory req/limit1Gi / 1Gi
Thread modelEvent loop (WebFlux)
HPA metricActive connections
Each open WebSocket holds state in memory (session, subscriptions, send buffer) for its entire lifetime — unlike HTTP where memory is freed after each response. 10,000 concurrent connections at 20KB per session = 200Mi memory overhead independent of business logic. Use WebFlux (Netty event loop) not Tomcat — traditional 1-thread-per-connection WebSocket on Tomcat will exhaust threads at a few thousand connections. Scale on active connection count, not CPU.

The critical decision: buffer or stream. Buffering a 100MB upload into a byte array uses 100MB of heap per concurrent request — 10 concurrent uploads = 1Gi heap pressure immediately. Always stream to disk or S3 directly using Spring's StreamingResponseBody or multipart streaming. Set spring.servlet.multipart.max-file-size and max-request-size appropriately. Append-only writes, event publishing
CPU request250m

Memory req/limit512Mi / 512Mi
Replicas2+ (stateless)
Throughput profileHigh write, low read
Command side is typically lightweight — validate command, write event to store, publish to Kafka/bus. Objects are short-lived (young-gen GC handles them well). G1GC default is fine. Ensure commands are idempotent and the service is truly stateless — multiple replicas must be able to handle the same command without coordination. HPA on CPU works well here.
📊
CQRS — Query / Projection Side
Read models, projection rebuilds
CPU request500m (rebuild: 2000m)
CPU limit2000m
Memory req/limit1Gi / 2Gi (rebuild window)
GCZGC (large projection maps)
Critical riskProjection rebuild on startup
Normal read traffic is low-cost. The danger is projection rebuild — replaying the entire event store to reconstruct the read model. This is CPU and memory intensive, can take minutes, and happens on every cold start unless the projection is checkpointed. During rebuild, heap can grow 3–5× normal operating level. Set memory limit to handle rebuild peak, not steady-state. Extend startup probe failureThreshold to cover rebuild time. Use ZGC if projection maps are large (millions of entries). Always checkpoint projections to storage to avoid full rebuilds.
🧱
Cache-Aside Service
Caffeine local cache, Redis L2
CPU request250m
CPU limitOmit
Memory req/limitheap + cache size + 256Mi
GCG1GC + UseStringDeduplication
Critical configCap cache by weight, not count
In-memory caches (Caffeine) live inside the JVM heap and must be included in the memory budget. A cache of 1M entries of average 1KB each = 1Gi of heap consumed by cache alone. Always size Caffeine by weight (maximumWeight) not count (maximumSize). Formula: container limit = MaxRAMPercentage heap + cache max size + 256Mi non-heap. Prefer Redis (off-heap, shared) for caches > 500Mi — keeps JVM heap small and cache survives pod restarts. Enable -XX:+UseStringDeduplication (G1GC only) if keys are String-heavy — can reduce heap 10–20%.
🛡️
Resilience4j Bulkhead Service
ThreadPoolBulkhead per downstream
CPU request500m
CPU limitOmit
Memory req/limit768Mi / 768Mi
Thread overhead+N threads per bulkhead
Key riskBulkhead thread stacks unaccounted
Each ThreadPoolBulkhead creates a dedicated thread pool per downstream dependency. 5 downstreams × 10 threads each = 50 extra threads = ~12Mi extra thread stacks on top of Tomcat's pool. This is frequently not counted in memory budgets. Add all bulkhead thread pools to your memory calculation. SemaphoreBulkhead (the simpler alternative) does not create extra threads — prefer it when you don't need request queuing. Also account for circuit breaker metrics accumulation: Resilience4j's sliding window stores N call results in a ring buffer per circuit — at high throughput this can consume hundreds of MB if window sizes are too large.
📬
Notification / Outbound Service
Email, SMS, webhook, push
CPU request100m–250m
CPU limit500m
Memory req/limit512Mi / 512Mi
Replicas2 (with deduplication)
Critical riskDuplicate sends on retry
CPU and memory are low — most time is spent blocked on external SMTP/SMS/push API calls. The real engineering challenge is correctness: at-least-once delivery from Kafka or a retry queue means the same notification may be triggered twice (pod restart mid-send, offset not committed). Use an idempotency key (message ID stored in DB/Redis) checked before each send. Always implement provider rate limiting (token bucket per provider API). Failed sends must go to a dead-letter queue, not be silently dropped — monitor DLQ depth as the primary SLA metric.
🔁
Long-Poll / Workflow Orchestrator
Temporal, Spring Integration, saga engine
CPU request500m
CPU limit1000m
Memory req/limit1Gi / 1Gi
Replicas2 (with sticky routing)
State storageExternal DB (mandatory)
Workflow instances can span hours or days. The JVM heap cannot hold workflow state across pod restarts — all in-flight workflow state must be persisted externally (Temporal DB, Spring Integration MessageStore, or custom saga table). Correlation IDs must be stored durably so any replica can resume. CPU is moderate but spiky at step transitions. Increase terminationGracePeriodSeconds significantly — a pod killed mid-step may leave a workflow in an ambiguous state if the step is not idempotent. Design every workflow step to be safe to re-execute.

Should You Set a CPU Limit? (Decision Tree)

CPU Limit Decision — work through in order

1️⃣Is this a batch job or offline task?
Yes → Set a CPU limit (2–4× request). Finite jobs bursting fully is acceptable and desirable. A limit prevents them from monopolising the node for hours.
2️⃣Is P99 latency a hard SLA (< 200ms)?
Yes → Omit CPU limit. CFS throttle fires in 100ms windows — even a brief burst above the limit can add up to ~100ms of latency. Removing CPU limits on latency-sensitive services is a widely-advocated practice for exactly this reason (see the Omio post and kubernetes/kubernetes #67577 in §13).
3️⃣Is node overcommit a concern?
If you omit limits, ensure a LimitRange is set on the namespace so unbounded pods cannot consume entire nodes. Also set resource quotas at namespace level.
4️⃣Is this a Kafka consumer?
Set a limit at 2–4× request. Consumer poll loops burst CPU during deserialization; a limit prevents one consumer starving the Kafka broker connection threads on shared nodes.
5️⃣Default for everything else
Omit CPU limit if you have VPA in recommendation mode. Monitor container_cpu_cfs_throttled_seconds_total — if throttle ratio exceeds 25%, remove the limit.
🏭 Industry Practice
Removing CPU limits on latency-sensitive workloads — while keeping requests and a namespace LimitRange as a safety net — is a well-established pattern in the Kubernetes community. The canonical references are Omio's post "Make your services faster by removing CPU limits" and the long-running kubernetes/kubernetes issue #67577 on CFS-quota throttling (both cited in §13). The pairing to apply on this platform: omit CPU limits, keep CPU requests, and govern with HPA plus VPA recommendations rather than hard ceilings.

Sizing for the Startup CPU Spike

Spring Boot services use a burst of CPU at startup — JIT compilation, class loading, component scanning, bean instantiation, and connection-pool warmup all happen in the first seconds. A common mistake is to raise the CPU request to cover that spike. Don't. The spike is transient; the request is a 24/7 reservation. Sizing the request for a 20-second startup event permanently wastes node capacity and ruins bin-packing.

The key insight: the request is a floor, not a ceiling. A pod can use far more CPU than its request during startup — provided the node has spare capacity and no CPU limit caps it. With a 250m request and no limit, the JVM can freely burst to 1500m+ while booting, then settle back to its steady-state usage. The request never throttles you; only a limit does.
Figure 1 — The startup CPU burst is transient. Size the request for steady-state; let the pod burst through startup by omitting the CPU limit. A limit set near steady-state (red) throttles the boot and can fail the startup probe.

If you must keep a CPU limit

If policy forces a CPU limit, the startup spike gets throttled — slowing the boot, which can trip the startup probe into a restart loop. Address it in this order:

ApproachWhat it doesTrade-off
Generous startupProbeGives a throttled boot room to finish before liveness kills it (e.g. failureThreshold: 20)Slower first-ready time; no downside otherwise
Reduce startup workCDS / AOT / lazy-init cut the CPU the JVM needs at boot (see table below)Build complexity or slower first request
Startup resource boostGive extra CPU only during boot, then scale downPlatform-specific / newer (see note)
Startup boost & in-place resize. Two newer mechanisms give extra CPU just for boot, without permanently inflating the request: GKE Autopilot's workload startup CPU boost, and Kubernetes In-Place Pod Resize (KEP-1287, beta in Kubernetes 1.33) which lets you raise then lower requests without restarting the pod. Both are recent — verify availability on your cluster before relying on them.

Recommended approaches to reduce startup cost

These cut the actual CPU and wall-clock the JVM spends starting, so the spike is smaller and shorter. Ordered from least to most invasive:

Recommended for this platform (Java 21 + Spring Boot 3.5): start with CDS (first-class in Spring Boot 3.3+) plus a generous startup probe — it needs no special JDK and no code changes. Add lazy-init for non-Kafka services. Reach for CRaC or Native Image only when you need near-instant startup (e.g. scale-to-zero, or minimising Kafka consumer lag during rolling deploys). See §6 — Spring Boot 3/4 & JDK 17+ Cloud Features for version details.

2 JVM & Spring Boot Memory Configuration

Container-Aware JVM — Why It Matters

Before Java 10, the JVM could not see cgroup limits — it sized the heap against the full host RAM. A container with 512Mi limit on a 64Gi node would default to a 16Gi heap and immediately OOMKill. UseContainerSupport (default on since Java 10) reads the cgroup v1/v2 memory limit instead.

Figure 2 — How the JVM lives inside a Kubernetes pod. The container-aware JVM sizes the heap as a percentage of the pod's cgroup memory limit — but everything else (Metaspace, thread stacks, code cache, direct buffers, GC structures, OS) must also fit inside the same limit, or the kernel OOMKills the container.
✅ Container-aware (MaxRAMPercentage) — Recommended
  • Portable — works regardless of container size
  • Scales correctly with VPA/HPA pod resizing
  • No manifest sync required when memory limit changes
  • Industry default (GKE, EKS runbooks both recommend this)
-XX:MaxRAMPercentage=75.0
-XX:InitialRAMPercentage=50.0
⚠️ Explicit heap (-Xms / -Xmx)
  • Easy to reason about in isolation
  • Breaks silently if container limit is changed without updating JVM flags
  • Over-allocates heap if container is scaled up by VPA
  • Under-allocates if container is right-sized down
-Xms256m -Xmx512m
When to use explicit heap anyway: If the service has a known, fixed workload (e.g., a sidecar with a tight memory budget of exactly 128Mi) and you need to guarantee no heap growth beyond a specific value. Use both: -XX:MaxRAMPercentage=75 -Xmx384m — whichever is lower wins.

Full Memory Budget Breakdown

Container memory = Heap + Non-heap. Non-heap is often underestimated. Here is the full breakdown for a 768Mi container with MaxRAMPercentage=70 (not 75 — see the warning below):

RegionTypical allocationControlled byCommon mistake
JVM Heap≈ 537Mi (70%)MaxRAMPercentageSetting too high leaves nothing for non-heap
Metaspace80–128Mi-XX:MaxMetaspaceSize=128mUncapped metaspace can grow until OOMKill
Thread stacks25–50Mi (100 threads × 256KB)-Xss256kTomcat with 200 threads = 50Mi unaccounted
Code cache (JIT)40–64Mi-XX:ReservedCodeCacheSize=64mOften forgotten in budget calculations
Direct / off-heap20–50Mi-XX:MaxDirectMemorySizeNetty, NIO — grows silently and causes OOMKill
GC internal20–40MiGC algorithmZGC has higher GC overhead than G1 at small heaps
OS + runtime~50MiOSNot visible in JVM metrics
Total non-heap235–382Mi—537 + 382 = 919Mi — already over 768Mi at the high end
The 75% rule breaks on 768Mi containers. 768Mi × 75% = 576Mi heap. Minimum realistic non-heap (Metaspace 80Mi + stacks 25Mi + code cache 40Mi + GC 20Mi + OS 50Mi) = ~215Mi. 576 + 215 = 791Mi — already over the 768Mi limit before a single direct buffer is allocated. Use 70% (537Mi heap) on 768Mi containers. Only push to 75% on containers ≥ 1Gi where non-heap overhead is proportionally smaller relative to heap.
The reactive/Netty trap. WebFlux and Netty allocate large pools of direct memory that live outside the JVM heap. A service with MaxRAMPercentage=75 in a 512Mi container uses 384Mi heap — but Netty may allocate another 100–150Mi direct buffer. Total = 530Mi → OOMKill. For reactive services, reduce MaxRAMPercentage to 60–65% and set -XX:MaxDirectMemorySize=128m.

MaxRAMPercentage Decision Tree

Choosing MaxRAMPercentage by service characteristics

📦Container ≤ 512Mi
60%. Non-heap overhead is nearly fixed (metaspace, threads, OS) — in small containers it is proportionally large. A 512Mi × 75% = 384Mi heap leaves only 128Mi for everything else, which is insufficient.
📦Container 512Mi–1Gi + Spring MVC
70%. Standard Spring Boot Tomcat service. Non-heap overhead is 200–250Mi minimum. At 768Mi × 70% = 537Mi heap + ~230Mi non-heap = 767Mi — just within budget. Using 75% on a 768Mi container pushes heap to 576Mi, leaving only ~192Mi for non-heap which is insufficient once thread stacks, code cache and OS overhead are counted. Reserve 75% for containers ≥ 1Gi.
⚡Container any size + WebFlux/Netty
60–65%. Netty direct memory pools are proportional to request throughput. Always cap with -XX:MaxDirectMemorySize=128m and monitor jvm_memory_used_bytes{area="nonheap"}.
📨Kafka consumer with large messages
65–70%. Deserialised messages live in heap until processed. For Avro/Protobuf at high throughput, heap fills faster than a REST service. Monitor young-gen GC frequency.
🗄️Bulky service with in-memory cache
75–80%. Non-heap is relatively smaller. Use ZGC to avoid long pauses during large heap collections. Set a cache size cap independent of heap to prevent unbounded growth.
⏰Batch / Spring Batch job
80%. Jobs are finite — no long-running thread stacks to accumulate. Set a high percentage but add -XX:+ExitOnOutOfMemoryError so OOM terminates the job cleanly rather than hanging.

The widely-followed pattern: keep G1GC as the default for the vast majority of services, and switch to ZGC selectively for large-heap (> 1Gi) latency-sensitive services where G1's stop-the-world pauses start cascading into downstream timeouts. See the OpenJDK ZGC project pages and JEP 377 / JEP 439 (§13).

3 Choosing a Garbage Collection Strategy

Every collector trades off three things you cannot maximise at once: throughput (CPU spent on application vs GC), latency (length of stop-the-world pauses), and footprint (memory and CPU overhead the GC itself needs). Picking a GC is really picking which two of those three matter most for a given service.

Figure 3 — The GC trade-off triangle. G1GC sits in the middle as a balanced default; the specialised collectors each pull toward one corner. Choose by which corner your service actually needs.

How to actually decide — measure, don't guess. Turn on unified GC logging (-Xlog:gc*:file=/tmp/gc.log:t,uptime,level,tags) or export JVM GC metrics via Micrometer/OTel (jvm_gc_pause_seconds), run a representative load test, and look at: pause duration p99, GC frequency, allocation rate, and % time in GC. Only switch away from G1GC when the data shows G1 pauses are actually breaching your latency budget. See the per-pattern quick reference in §2 (GC Selection by Service Pattern).
Generational ZGC matters. Original (non-generational) ZGC collected the whole heap every cycle, which hurt throughput on services with high allocation rates. Generational ZGC (JEP 439, Java 21) collects young and old generations separately — far more efficient for typical web workloads. On Java 21 it is opt-in (-XX:+ZGenerational); from Java 23 it became the default and the non-generational mode was deprecated, then removed in a later release. Prefer generational ZGC whenever you choose ZGC.

4 Kubernetes Best Practices

Probes — Rationale and Tuning

Kubernetes has three probe types. Using the wrong type for the wrong check causes either premature pod kills or traffic sent to an unready pod — both are production incidents.

ProbeEndpointRuleWrong usage consequence
Startup /actuator/health/readiness Covers JVM warmup + context init. Until this passes, liveness is disabled. Without startup probe: liveness fires at 10s and kills a perfectly healthy service still loading Spring beans
Liveness /actuator/health/liveness Must be cheap — just check the JVM is alive. Never include DB or external checks. If DB goes down and liveness checks DB → all pods killed → outage. Liveness should only kill a deadlocked JVM.
Readiness /actuator/health/readiness Check dependencies (DB, cache, downstream). Pod removed from endpoints if fails. Without readiness: gateway routes to a pod whose DB connection pool is exhausted → request errors

Probe timing by service startup characteristics

🚀Lightweight service (< 5s start)
Startup probe: initialDelaySeconds: 5, failureThreshold: 6 (30s window). Typical for services with lazy initialisation enabled.
🐢Typical Spring Boot (5–30s start)
Startup probe: initialDelaySeconds: 20, periodSeconds: 10, failureThreshold: 12 (140s window). This is the golden standard.
🐘Bulky service with Flyway/Liquibase migrations
Startup probe: initialDelaySeconds: 30, periodSeconds: 15, failureThreshold: 20 (330s window). DB migrations can take minutes on first deploy.
📨Kafka consumer waiting for broker
Extend startup window — consumer will retry broker connection. Set failureThreshold: 24 (4min window). Also set spring.kafka.consumer.max-poll-interval-ms higher than startup probe window.
# Golden standard probe config — adjust only initialDelaySeconds and failureThreshold
startupProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  initialDelaySeconds: 20
  periodSeconds: 10
  failureThreshold: 12    # 20 + (12 × 10) = 140s total startup window
  timeoutSeconds: 5
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 15
  failureThreshold: 3     # 45s of consecutive failure before restart
  timeoutSeconds: 5
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 5

Graceful Shutdown — The Full Chain

Graceful shutdown involves a chain of events across Kubernetes and Spring. Getting any one step wrong causes dropped requests or pods being killed mid-flight.

StepActorWhat happensConfig
1KubernetesMarks pod Terminating, removes from endpointsAutomatic on delete/rollout
2kube-proxy / iptablesStops routing new requests to the podTakes 1–5s propagation time
3preStop hookRuns before SIGTERM — bridges the propagation gappreStop: exec: sleep 5
4Spring BootReceives SIGTERM, stops accepting new requests, drains in-flightserver.shutdown: graceful
5Spring BootWaits for active requests to complete, then shuts downspring.lifecycle.timeout-per-shutdown-phase: 30s
6KubernetesSends SIGKILL after grace periodterminationGracePeriodSeconds: 60
The most common misconfiguration. Setting terminationGracePeriodSeconds: 30 while Spring's shutdown timeout is also 30s leaves zero margin. If Spring takes 31s to drain, Kubernetes kills the JVM mid-drain. Always: terminationGracePeriodSeconds = Spring timeout + preStop delay + 15s buffer. With 30s Spring + 5s preStop: set terminationGracePeriodSeconds: 60.

Graceful shutdown tuning by service pattern

📨Kafka consumer
On SIGTERM, the consumer must complete the current poll batch and commit offsets before shutdown. Set spring.kafka.listener.immediate-stop: false and increase Spring shutdown timeout to 60s. Total grace period: 90s.
⏰Scheduler with long-running jobs
Use @Async task executor with a custom shutdown hook, or use Spring's TaskExecutorFactoryBean with waitForTasksToCompleteOnShutdown=true. Grace period must cover the longest job duration.
🔀Saga / state machine
Persist saga state to DB before shutdown. Spring State Machine supports a StateMachinePersister — ensure state is written before the JVM exits. Otherwise, in-flight sagas are lost.
🌐REST API (default)
Standard 30s Spring + 5s preStop. Increase only if requests routinely take > 10s (e.g., report generation).

🏭 Common Practice
KEDA is the common choice for autoscaling Kafka consumers. Scaling on CPU is almost always wrong here — a consumer can sit near 0% CPU while its lag grows into the millions (it is blocked on I/O, e.g. a slow downstream DB). KEDA's Apache Kafka scaler adds and removes replicas based on consumer lag — the metric that actually reflects pressure. KEDA is a CNCF project; see keda.sh (§13). Remember effective parallelism is still capped by partition count.

Pod-level (applies to all containers)

5 Performance Tuning by Pattern

Virtual Threads (Java 21) — The Game Changer

✅ Virtual Threads — Enable if on Java 21 + Spring Boot 3.2+
  • Eliminates Tomcat thread pool sizing entirely
  • Each request gets its own lightweight thread (not OS thread)
  • Removes HikariCP starvation under bursty, I/O-heavy load
  • Fan-out services (calling 5 downstream APIs) no longer need large thread pools
  • Kafka consumers: each poll invocation can run on a virtual thread
⚠️ Watch out for with Virtual Threads
  • Synchronized blocks pin virtual thread to OS thread — a pinning anti-pattern
  • JDBC drivers: some older drivers have synchronized in hot paths (check driver version)
  • ThreadLocal-heavy code may behave unexpectedly at millions of virtual threads
  • Debugging and profiling tools may not yet show virtual thread stacks properly
# Enable virtual threads (Java 21 + Spring Boot 3.2+)
spring.threads.virtual.enabled: true

# These become unnecessary with virtual threads:
# server.tomcat.threads.max: 200
# server.tomcat.threads.min-spare: 10
# spring.datasource.hikari.maximum-pool-size: 20  (can keep but pool behaviour changes)
🏭 Common Practice
On Java 21 + Spring Boot 3.2+, enabling virtual threads (spring.threads.virtual.enabled=true) is the recommended default for new I/O-bound services — Spring Boot exposes this as a first-class flag. The main thing to watch at scale is pinning: run -Djdk.tracePinnedThreads=full in staging and fix any pinning sites (typically synchronized held across blocking calls) before production. See the Spring Boot reference docs and JEP 444 (§13).

HikariCP pool size decision tree

🌐Stateless REST API
maximum-pool-size = Tomcat threads / 2. Not all requests hit the DB. A 100-thread Tomcat service typically needs 20–30 DB connections max.
📨Kafka consumer
Pool = number of listener threads × avg DB calls per message. A consumer with 4 threads each making 2 DB calls needs at least 8 connections. Add 25% headroom.
⏰Batch / scheduler
Pool = Spring Batch concurrency (step chunk threads). Keep minimum-idle low (2) since the service is mostly idle. Burst during batch run is fine.
⚠️connection-timeout firing in logs?
Don't just increase pool size — first check if DB max_connections is exhausted across all pods. max pool × pod count ≤ DB max_connections × 0.8.

7 Sizing Methodology

Step-by-step sizing process for a new service

1️⃣Identify service pattern
Use the pattern cards in §1. Is it a Kafka consumer? Scheduler? Bulky data service? This determines the starting point for requests and which GC to use.
2️⃣Deploy with no limit
Set a conservative request (250m CPU / 512Mi memory), no limits. Deploy to staging and run a representative load test (k6). Observe actual peak usage via Prometheus.
3️⃣Collect these metrics
container_cpu_usage_seconds_total (p95/p99 under load)
container_memory_working_set_bytes (peak, not average)
jvm_memory_used_bytes{area="heap"} and area="nonheap"
jvm_gc_pause_seconds_sum / count (average pause)
hikaricp_connections_pending (pool starvation signal)
4️⃣Set request
CPU request = p95 CPU under normal load + 20%. Memory request = peak working set + 20%. Both should be achievable on your node types.
5️⃣Set limit
Memory limit = request (Guaranteed QoS). CPU limit: see §1.4 decision tree. For most APIs: omit. For batch/Kafka: 2–4× request.
6️⃣Run VPA in Off mode
Deploy updateMode: "Off" VPA for 7 days in production. Review kubectl describe vpa recommendations. Adjust requests if VPA suggests materially different values.
7️⃣Set continuous alerts
Alert on: container_oom_events_total > 0 (memory too low)
Alert on: cpu_throttled_ratio > 25% (CPU limit too low or should be removed)
Alert on: hikaricp_connections_pending_total > 0 sustained (pool too small)

10 Platform Team Deployment Checklist

Resource Configuration

  • CPU request set and based on measured p95 load (not a guess) Reference: Prometheus query rate(container_cpu_usage_seconds_total[5m]) at p95
  • Memory request = memory limit (Guaranteed QoS) Exception: batch jobs may use Burstable (request < limit)
  • CPU limit decision documented: omitted (latency-sensitive) or set (batch/Kafka) See §1.4 decision tree
  • JAVA_TOOL_OPTIONS includes -XX:+UseContainerSupport Without this, JVM may size heap against host RAM, not container limit
  • MaxRAMPercentage set based on service pattern (60–80%) Reactive/Netty: 60–65%. Standard MVC: 70–75%. Batch: 80%
  • MaxMetaspaceSize explicitly capped at 128m (or measured value) Uncapped Metaspace can grow unboundedly and cause unexpected OOMKill

Reliability

  • startupProbe covers the full JVM + Spring context initialisation window
  • livenessProbe endpoint is lightweight (no DB/external calls)
  • readinessProbe endpoint checks dependencies (DB, downstream, cache)
  • terminationGracePeriodSeconds ≥ Spring shutdown timeout + preStop + 15s
  • preStop: sleep 5 hook present to bridge kube-proxy propagation delay
  • server.shutdown: graceful in application config
  • spring.lifecycle.timeout-per-shutdown-phase: 30s in application config
  • minReplicas ≥ 2 in production
  • PodDisruptionBudget created for all services with minReplicas ≥ 2

Pattern-Specific Checks

  • Kafka consumers: replicas ≤ partition count; KEDA configured on lag metric HPA on CPU is wrong for Kafka consumers — scale on lag, not CPU
  • Schedulers: ShedLock or leader election configured if replicas > 1 Multiple replicas without leader election = duplicate job runs
  • Schedulers: spring.task.scheduling.pool.size ≥ concurrent schedule count
  • @Async: custom bounded executor configured (not default SimpleAsyncTaskExecutor) Default unbounded executor can exhaust threads silently under load
  • State machines / sagas: state persisted externally (DB/Redis) — not in-memory
  • Reactive/WebFlux: MaxRAMPercentage ≤ 65% and MaxDirectMemorySize set

Scheduling & HA

  • TopologySpreadConstraints or podAntiAffinity prevents all replicas on same node

  • Rolling update: maxUnavailable: 0 for zero-downtime deploys

Security

  • runAsNonRoot: true + runAsUser: 1000 at pod level
  • allowPrivilegeEscalation: false + readOnlyRootFilesystem: true at container level

  • Image tagged with Git SHA — never :latest

Observability

11 Illustrative Failure Scenarios

The scenarios below are composite illustrations of well-documented failure modes, not verbatim accounts of specific named-company incidents. Each describes a realistic situation, the underlying mechanism (which is real and verifiable), and the fix. Where a topic has a genuine public write-up, it is cited explicitly. Treat the numbers as representative, not as measured results from a particular production system.

On honesty. These are teaching scenarios. The mechanisms — CFS throttling, GC pause cascades, consumer rebalance storms, Metaspace exhaustion, virtual-thread pinning, duplicate schedulers — are all real and reproducible. The specific figures are illustrative.
CFS Throttling
Failure mode CPU limits
Latency spikes at low average CPU — the CPU-limit throttling trap

A latency-sensitive REST service shows P99 spikes of 150–200ms while average CPU sits around 30%, nodes are not saturated, and GC pauses are under 20ms. The cause is Linux CFS (Completely Fair Scheduler) bandwidth throttling — a distinct problem from the more commonly known noisy neighbour issue.

Noisy neighbour is when one pod consumes so many shared resources that it degrades other pods on the same node. CFS throttling is different — it harms only the pod that has a CPU limit set, even when the node has spare capacity. The CFS scheduler enforces limits in 100ms accounting periods. A service with limit: 500m is allowed to run for 50ms per 100ms window. If a request triggers a burst to 600m for even a few milliseconds, the container is frozen for the remainder of that 100ms window — even if the node is sitting at 20% utilisation. The application experiences this as a latency spike with no corresponding high CPU metric, because the CPU was throttled, not saturated.

Fix: Remove the CPU limit from latency-sensitive services and rely on requests + HPA for governance, with a namespace LimitRange as the safety net. This is a genuinely debated topic — see Omio's widely-cited post "Kubernetes: Make your services faster by removing CPU limits" and the long-running discussion in kubernetes/kubernetes issue #67577 (kernel CFS quota throttling).
📌 Lesson for this platform: Omit CPU limits on stateless REST APIs and gateway services. Monitor container_cpu_cfs_throttled_seconds_total — if the throttled ratio exceeds ~25%, remove the limit.
GC Pause Cascade
Optimisation ZGC
Large-heap G1GC pauses cascading into downstream timeouts

A service carrying a 4–8Gi heap on G1GC experiences major collection pauses in the hundreds of milliseconds under peak load. Because the pod is unresponsive during a stop-the-world pause — even though its readiness probe still passes between pauses — callers begin timing out, and the timeouts cascade through synchronous dependency chains.

ZGC (production-ready since Java 15 via JEP 377; Generational ZGC added in Java 21 via JEP 439) performs almost all of its work concurrently with application threads, keeping stop-the-world pauses sub-millisecond largely independent of heap size. The trade-offs are a modest throughput cost (single-digit to low-double-digit percent) and higher memory overhead.

Fix: For large-heap, latency-sensitive services, switch from G1GC to ZGC and budget extra container memory for ZGC's overhead. The sub-millisecond-pause claim is documented in the OpenJDK ZGC project pages and JEP 377 / JEP 439.
📌 Lesson for this platform: Any service with heap > 1Gi processing latency-sensitive requests should evaluate ZGC, sizing the container limit to include the added GC overhead.
Rebalance Storm
Failure mode Kafka consumer
Kafka consumer lag explosion during a rolling deploy

A consumer service runs one pod per partition. During a rolling deployment, Kubernetes drains pods one at a time. Spring Boot's graceful shutdown waits for in-flight HTTP requests, but the Kafka consumer has no matching grace for committing offsets — so pods are killed mid-poll. Each pod removal triggers a consumer-group rebalance, and a rebalance pauses consumption for the whole group while partitions are reassigned. Across a full rolling deploy this can mean many consecutive rebalances, and lag grows sharply during the deployment window.

Fix: Set spring.kafka.listener.immediate-stop: false so a consumer finishes its current batch and commits offsets before stopping, and raise terminationGracePeriodSeconds (e.g. to 90s) to give that drain time to complete. Consumer-group rebalance behaviour is documented in the Apache Kafka and Spring for Apache Kafka docs.
📌 Lesson for this platform: Kafka consumer graceful shutdown needs explicit configuration — default Spring shutdown does not wait for offset commits. Set immediate-stop: false and extend the grace period.
Wrong Scale Metric
Optimisation KEDA · Kafka
CPU-based autoscaling that never fires for an I/O-bound consumer

A Kafka consumer fleet scales on CPU via HPA. Under a traffic surge, consumer lag grows into the millions while CPU stays low — because the bottleneck is downstream database write latency, not CPU. The consumers spend most of their time blocked on I/O (low CPU), so HPA never crosses its CPU threshold and never adds replicas. By the time CPU finally rises, a large backlog has accumulated and takes a long time to drain.

The fix is to scale on the metric that actually reflects pressure: consumer lag. KEDA's Kafka scaler adds replicas based on lag thresholds, independent of CPU, and scales back down as lag clears.

Fix: Replace CPU-based HPA with KEDA's Kafka scaler driven by consumer lag. See the KEDA documentation (keda.sh) for the Apache Kafka scaler. Remember that effective parallelism is still capped by partition count.
📌 Lesson for this platform: Don't scale Kafka consumers on CPU. Lag is the meaningful signal — use KEDA's Kafka scaler for event-driven consumer autoscaling.
Metaspace Leak
Failure mode OOMKill
Silent OOMKill from uncapped Metaspace — the invisible leak

A service is OOMKilled periodically in production, yet JVM heap metrics show no growth — heap usage is stable. Raising the container memory limit only delays the kill. A native-memory inspection (jcmd <pid> VM.native_memory, with NativeMemoryTracking enabled) reveals Metaspace steadily growing.

The classic root cause is runtime class generation: a dynamic bytecode library (CGLIB, Byte Buddy, ASM — often pulled in transitively) that generates new classes without unloading them. Each generated class consumes Metaspace. With no MaxMetaspaceSize set, Metaspace grows until the container's cgroup limit is hit — while heap metrics look perfectly healthy the whole time.

Fix: Cap Metaspace explicitly (e.g. -XX:MaxMetaspaceSize=128m, sized after profiling) so the failure surfaces quickly and unmistakably as Metaspace pressure, then track down and remove the class-generating dependency. Metaspace behaviour is documented in the OpenJDK / HotSpot JVM docs.
📌 Lesson for this platform: Always cap Metaspace. A fast, obvious failure beats a slow, mysterious one. Audit transitive dependencies for runtime bytecode generation (CGLIB, Byte Buddy, ASM).
VT Pinning
Migration Virtual threads
Java 21 virtual threads — and the pinning gotcha

A synchronous REST service that fans out to several downstream services per request is a textbook candidate for virtual threads: threads spend most of their time parked on I/O. On Java 17 it needs a large Tomcat thread pool and carefully tuned HikariCP sizing to avoid connection starvation under load.

Enabling spring.threads.virtual.enabled=true on Java 21 + Spring Boot 3.2+ lets each request run on its own virtual thread, which unmounts from its carrier OS thread while parked on I/O — so platform thread-pool sizing largely stops mattering and connection-pool pressure eases. The common gotcha: a synchronized block held across a blocking call pins the virtual thread to its carrier, negating the benefit.

Fix: Roll virtual threads out to fan-out / I/O-bound services first, and run with -Djdk.tracePinnedThreads=full in staging to find and fix pinning sites before production. Pinning is documented in JEP 444 and the Project Loom material. On JDK 24+ this caveat largely goes away — JEP 491 makes synchronized no longer pin a virtual thread to its carrier (see §6).
📌 Lesson for this platform: On Java 21, enable virtual threads on fan-out services first and scan for pinning with -Djdk.tracePinnedThreads=full. A move to JDK 24+ (JEP 491) removes the synchronized-pinning concern.
Duplicate Scheduler
Failure mode No leader election
A @Scheduled job that runs once per replica

A service runs a @Scheduled job and is deployed with multiple replicas for availability. Because @Scheduled fires independently in every JVM, the job runs once per replica on every tick. If the job calls a rate-limited external API or performs non-idempotent writes, the duplicate executions multiply load and can cause incorrect results or trip a downstream rate limiter — and the problem gets worse exactly when you scale out.

Fix: Add distributed locking so only one replica runs each tick. ShedLock (github.com/lukas-krecan/ShedLock) is the common Spring choice, with JDBC or Redis lock providers; Quartz in clustered mode is an alternative. This lets you scale replicas freely without changing job execution.
📌 Lesson for this platform: Any @Scheduled job on a service with more than one replica needs distributed locking (ShedLock) or clustered scheduling. Never assume only one replica runs the task.

Facts that are non-obvious, frequently misunderstood, or just useful to know when working at this level.

🧊
The JVM doesn't return memory to the OS by default
After a traffic spike, GC reclaims heap objects but the JVM keeps the committed heap memory reserved. Container metrics show high memory even after load drops. Java 12+ introduced -XX:+ZUncommit (ZGC) and G1GC got -XX:G1PeriodicGCInterval=300000 to periodically return unused heap to the OS. Without this, a pod that processed a spike 30 minutes ago looks like it is still under memory pressure.
⏱️
Kubernetes endpoint propagation takes 1–5 seconds
When a pod is deleted, Kubernetes removes it from the Endpoints object. But kube-proxy on each node must receive and apply that update via watch. This takes 1–5 seconds depending on cluster size. During this window, the load balancer still sends traffic to a pod that has already received SIGTERM and is shutting down. This is exactly why preStop: sleep 5 exists — to bridge that propagation gap before Spring begins shutdown.
🔢
500m CPU means half a core — always
500m is 500 millicores = 0.5 vCPU regardless of whether the node has 2 cores or 128 cores. It represents a proportion of time, not a physical core allocation. A pod with request: 500m on a 4-core node is guaranteed at minimum 1/8th of the node's total CPU time under contention. On an idle node it can use far more — right up to any configured limit.
🪡
G1GC silently grows the heap to its maximum on the first major GC
With MaxRAMPercentage=75 and InitialRAMPercentage=50 on a 512Mi container, the JVM starts with ~256Mi committed heap. The first major collection that can't reclaim enough will expand the heap toward the 384Mi maximum — and keep it there. This is expected behaviour but confuses engineers who see memory grow steadily after startup and assume a leak. Monitor jvm_memory_committed_bytes vs jvm_memory_used_bytes — only the used metric indicates a genuine leak.
📊
OOMKilled vs OOM — they are different killers
Kubernetes OOMKills the container when it exceeds the cgroup memory limit (the limits.memory value). The JVM's own OutOfMemoryError fires when the heap is full (regardless of container limit). It is possible to have a JVM throw OutOfMemoryError: Java heap space while the container still has 200Mi free — because the heap is full but non-heap memory (Metaspace, direct buffers, thread stacks) has headroom. Always tune both: JVM heap percentage AND the total container limit to accommodate all memory regions.
🐘
Flyway/Liquibase runs on startup — in every replica simultaneously
When deploying a service with 5 replicas and a DB migration, all 5 pods start simultaneously and all 5 try to run Flyway on startup. Flyway uses a distributed lock (advisory lock or a flyway_schema_history table row) to ensure only one runs the migration. The other 4 wait. This waiting period can push startup beyond your startup probe window if migrations are slow. Always set a generous startup probe failureThreshold for services with Flyway — especially for the first deploy with a schema change.
🔄
Spring's @Transactional does not automatically retry on deadlock
Kafka consumers processing messages that write to a database under concurrent load frequently hit deadlocks. @Transactional will propagate the CannotAcquireLockException up to the Kafka listener — which retries the entire message. Without a retry limit, this can cause a message to be retried indefinitely, blocking the partition. Always configure a DefaultErrorHandler (Spring Kafka 2.8+; it replaced the now-removed SeekToCurrentErrorHandler) with a backoff and a DeadLetterPublishingRecoverer for production Kafka consumers.
🌍
Virtual threads bring a decades-old idea to the JVM mainstream
Lightweight user-mode threads ("M:N" scheduling) long predate Java's virtual threads — Erlang processes, early Java "green threads", and Go's goroutines (2009) all use the same core idea of many logical threads multiplexed over few OS threads. Project Loom — the effort to bring this back to the JVM — began around 2017, previewed in Java 19 (JEP 425, 2022), and reached GA in Java 21 (JEP 444, 2023). The significance: for I/O-bound services the OS-thread-per-request model was the main scaling ceiling, and virtual threads remove it without rewriting code in a reactive style.
💡
The Kubernetes scheduler never looks at actual usage — only requests
When placing a pod, the scheduler sums up all existing pods' requests on a node and checks if the new pod's request fits in the remaining capacity. It does not look at current CPU or memory utilisation at all. A node at 5% actual CPU usage can still reject a new pod if existing pods' requests sum to 95% of node capacity. This is why "the node has plenty of CPU but pods won't schedule" is such a common confusion — and why right-sizing requests (not just limits) matters.
