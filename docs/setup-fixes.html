Fixed in the Repo

1. bootstrap.ps1 — bash heredocs in a PowerShell script

Symptom: the dashboard step fails. kubectl apply -f - <<EOF is bash syntax; PowerShell has no heredoc.

Fix: pipe a PowerShell here-string into kubectl. The kubectl patch to NodePort was dropped — the Service manifest below already sets type: NodePort.

# Before (bash only)
kubectl apply -f - <<EOF
apiVersion: v1
kind: Service
...
EOF

# After (PowerShell)
@"
apiVersion: v1
kind: Service
...
"@ | kubectl apply -f -

2. Argo Rollouts CRDs rejected — "metadata.annotations: Too long"

Symptom:

CustomResourceDefinition "rollouts.argoproj.io" is invalid:
  metadata.annotations: Too long: may not be more than 262144 bytes

Cause: client-side kubectl apply stores the whole object in the last-applied-configuration annotation. The rollouts and analysisruns CRDs exceed the 256 KB annotation limit. The controller still installs, so bootstrap looks fine — but make deploy later fails with no matches for kind "Rollout".

Fix: server-side apply (no annotation stored):

kubectl apply --server-side -n argo-rollouts -f https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml

Cluster bootstrapped with the old script? Re-run the command with --force-conflicts and check all five CRDs exist:

kubectl get crd | findstr argoproj   # expect 5: analysisruns, analysistemplates, clusteranalysistemplates, experiments, rollouts

3. bootstrap.ps1 reported success when everything failed

Symptom: every kubectl call errored, yet the script printed "NGINX Ingress ready", "Argo Rollouts ready", "Bootstrap complete" and exited 0.

Cause: $ErrorActionPreference = "Stop" does not apply to native executables in Windows PowerShell 5.1 — a failing kubectl.exe just sets $LASTEXITCODE.

Fix: a wrapper at the top of the script shadows kubectl, so every call (including piped ones) stops the script on failure:

function kubectl {
    $input | & kubectl.exe @args
    if ($LASTEXITCODE -ne 0) { throw "kubectl $args failed (exit code $LASTEXITCODE)" }
}

Verified both ways: against an unreachable cluster it stops at step 1 with exit code 1; against the real cluster it completes all three steps with exit code 0.

4. make deploy fails — duplicate AnalysisTemplate

Symptom:

accumulating resources: may not add resource with an already registered id:
  AnalysisTemplate.v1alpha1.argoproj.io/smoke-test

Cause: employee/k8/analysis-template.yaml and department/k8/analysis-template.yaml both define smoke-test in the same namespace. Kustomize refuses duplicates, so nothing in the microservices namespace gets applied.

Fix: the files are identical apart from one comment, and the template is parameterized by preview-url, so both Rollouts share one copy:

  - department/k8/service-preview.yaml
  # department reuses the shared smoke-test AnalysisTemplate from employee/k8 (same name, parameterized by preview-url).
Long-term option. Move the template to a shared location (e.g. shared/k8/analysis-template.yaml) or make it a ClusterAnalysisTemplate, and delete the per-service copies so they can't drift apart.

5. https://dashboard.myorg.com returns 404

Cause: observability/k8/dashboard-ingress.yaml exists but no step applied it — it isn't in any kustomization, the Makefile or the bootstrap script.

Fix: bootstrap applies it right after installing the dashboard:

kubectl apply -f (Join-Path $PSScriptRoot "..\observability\k8\dashboard-ingress.yaml")

The manifest's ssl-passthrough annotation has no effect — ingress-nginx is installed without --enable-ssl-passthrough. NGINX serves its default "Kubernetes Ingress Controller Fake Certificate" and re-encrypts to the dashboard (backend-protocol: HTTPS). It works; the browser certificate warning is expected.

6. make health — every pod flagged as not ready

Symptom: pods are 1/1 Running, but the check prints [WARN] employee-... (/1) phase=Running for each one and exits 1.

Cause: in PowerShell 5.1, when Where-Object matches exactly one item it returns a single object, and .Count on a single PSCustomObject is empty. Every pod here has one container, so the ready count was always blank.

Fix: force arrays with @():

$ready = @($p.status.containerStatuses | Where-Object { $_.ready }).Count
$total = @($p.status.containerStatuses).Count

Environment Issues (no repo change)

7. x509: certificate signed by unknown authority — antivirus TLS interception

Symptom: kubectl fails — sometimes every call, sometimes randomly:

Unable to connect to the server: tls: failed to verify certificate:
  x509: certificate signed by unknown authority

Cause: Norton's Web/Mail Shield intercepts HTTPS to the Kubernetes API (kubernetes.docker.internal:6443, and at times 127.0.0.1:6443) and re-signs it with its own CA. Other antivirus products with "HTTPS scanning" (Avast, AVG, Kaspersky, ESET, Bitdefender) can do the same. Your kubeconfig and Docker Desktop's certificates are fine.

Diagnose (Git Bash) — check who issued the certificate:

echo | openssl s_client -connect kubernetes.docker.internal:6443 2>/dev/null | openssl x509 -noout -issuer
# good: issuer=CN=kubernetes
# bad:  issuer=... O=Norton Web/Mail Shield ...

Fix:

Turn off HTTPS scanning (reliable)

Norton → Settings → Antivirus → Web/Mail Shield → disable HTTPS scanning / Scan secure connections. The shield itself can stay on. Restart Docker Desktop.

Exceptions (not reliable on their own)

Same screen → Exceptions: kubernetes.docker.internal, 127.0.0.1, localhost, *.myorg.com. In testing, interception kept coming back with exceptions only.

Don't use insecure-skip-tls-verify. It turns off certificate checking for the cluster entirely.

8. kubectl fails for the first minute or two after Docker Desktop starts

Cause / Fix: the API server is still starting even when the whale icon is green. Wait until this succeeds before running bootstrap or make:

kubectl get nodes   # expect: docker-desktop   Ready
Git Bash gotcha while diagnosing. kubectl get --raw /version returns NotFound in Git Bash because MSYS rewrites /version into a Windows path. Test with kubectl get nodes instead.

Still Open

9. make up always pushes

make up = obs-up build push deploy ingress. REGISTRY lets you target your own Docker Hub account (make up REGISTRY=you, after docker login), but there's no target that skips the push — without a Docker Hub account, make up stops with denied.

Workaround: run the steps without push:

make bootstrap
make obs-up
make deploy ingress   # uses the public dayasahu6077/* images

Planned fix: a make local-up target (obs-up build deploy ingress) paired with #10.

10. Local-only path still runs Docker Hub images

With imagePullPolicy: Always the kubelet pulls $(REGISTRY)/*:latest from Docker Hub and ignores your local build. It works only because the default images are public — local code changes never reach the cluster. Files to change for local iteration (Always → IfNotPresent):

configserver/k8/deployment.yaml
auth-service/k8/deployment.yaml
ms-api-gateway/k8/deployment.yaml
employee/k8/rollout.yaml
department/k8/rollout.yaml

Planned fix: a kustomize patch in a local overlay rather than editing the base manifests.

11. Static dashboard token snippet is bash-only

The Setup Guide's long-lived token uses <<EOF and base64 -d. In PowerShell:

@"
apiVersion: v1
kind: Secret
metadata:
  name: admin-user-token
  namespace: kubernetes-dashboard
  annotations:
    kubernetes.io/service-account.name: admin-user
type: kubernetes.io/service-account-token
"@ | kubectl apply -f -

$t = kubectl -n kubernetes-dashboard get secret admin-user-token -o jsonpath="{.data.token}"
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($t))

12. Smoke-test curl in PowerShell 5.1

In Windows PowerShell 5.1, curl is an alias for Invoke-WebRequest, so -X/-H/-d fail. Use curl.exe, or run the commands in Git Bash:

curl.exe -X POST http://api.myorg.com/auth/token -H "Content-Type: application/json" -d "{\"userId\":\"12345\"}"

13. Installing kubectl-argo-rollouts

Download

From github.com/argoproj/argo-rollouts/releases, download kubectl-argo-rollouts-windows-amd64.

Rename

Rename it to kubectl-argo-rollouts.exe — kubectl finds plugins by this exact name.

Put it on PATH

Move it into a folder on your PATH (e.g. next to kubectl.exe, or create C:\tools and add it to PATH). Reopen the terminal.

Verify

kubectl argo rollouts version

14. API gateway shows 1 restart

On a fresh deploy the gateway can start before configserver is ready and restart once. It recovers on its own; RESTARTS 1 in make status is not a failure.
